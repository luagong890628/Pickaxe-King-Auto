## 1. 使用者的核心設計方向

以下都是使用者原話定案的，改動前不要推翻：

| # | 方向 | 使用者說法 |
| --- | --- | --- |
| 1 | **純機械化，不做畫面偵測** | 「不要再引入畫面偵測」——先前所有偵測／地圖／觸控重播都證明不穩並移除 |
| 2 | **時間軸起點 = 小村莊第一刀** | 「時間是從小村莊樹重生時間開始算的 4島不是主要」 |
| 3 | **四島只是補時，不是主線** | 「4島只是補時阿 樹重生了 還是要傳送到小村莊、起始之地去繼續砍樹 多的時間 才會到4島上」 |
| 4 | **島上停留是「至少」不是「限制」** | 「也不是限制就只走13秒 是至少13秒」 |
| 5 | **固定順序，不要權重抽選** | 「我想調整走島的路線 不是權重用抽的」 |
| 6 | **不要把重生時間寫進程式** | 「都是大約的 像是冰雪是108秒 4島之後還會再降低 我覺得不要把冷卻時間寫進去 就是固定順序」 |
| 7 | **一個窗口內每座島只去一次**（本次新增，由實測推導，使用者已同意方向） | — |

方向 6 的理由很重要：把 108 秒寫成門檻，會在「其實還能採」的時候擋掉那座島。所以程式裡**沒有任何重生秒數**，只用結構性規則（固定順序 + 一輪不回頭）。

> 補充：島嶼傳送實際門檻是 **13.0 秒**（`TELEPORT_COOLDOWN 12.0` + 每座島 1.0 緩衝，commit `9248d9c`）。
> 使用者要的是「至少 13 秒」，不是「只能走 13 秒」。這條規則現在對 `ice` 產生副作用，見 §6-A。

## 2. 排程實際長什麼樣

```
小村莊第一刀（village_first_cut）
   └─ +105 秒 = 村莊樹回來的硬邊界（VILLAGE_FIRST_CUT_INTERVAL）

期間：起始之地（100s 刷新）→ 自由農場A（240s 刷新，有到才去）
      → 主三區都在刷新 → 剩下的空檔才丟給島嶼
      → 邊界一到就無條件回村
```

對應程式：

| 位置 | 作用 |
| --- | --- |
| `cycle_fixed.py:371 next_stop()` | 只挑已刷新的主區；多個都好則挑「超過自己週期比例最大」的 |
| `cycle_fixed.py:802` `filler_visited = set()` | 主迴圈持有的「這個窗口已經逛過的島」 |
| `cycle_fixed.py:813` | 呼叫 `run_island_filler(rec, filler_deadline, filler_visited)` |
| `cycle_fixed.py:840` `filler_visited.clear()` | 小村莊重新採集（新的 first cut）→ 新窗口，清空 |
| `cycle_fixed.py:613 run_island_filler()` | 島嶼補空檔主體 |

**關鍵**：補空檔不是「連續跑滿 105 秒」。主區跑完剩多少才塞多少，所以窗口長度在 30～105 秒之間跳動（農場有沒有插進來差很多）。

## 6. 未決事項（接手後優先處理）

### A. `ice` 每趟多繞一圈 —— 建議修，但要先問使用者

現況（`captures/fixed_20261030_001157`）：

| 島 | 第 2 圈邊界 | 實際收手 | 圈數 |
| --- | --- | --- | --- |
| ice | **12.09s** | 16.94s | 3 圈 |
| shark | 13.87s | 13.87s | 2 圈 |
| duck | ~11.6s | 13.23s | 3 圈 |
| truffle | 13.71s | 13.71s | 2 圈 |

`ice` 的第 2 圈邊界 12.09s 差 0.91 秒過不了 13 秒冷卻門檻（`_teleport_cooldown_ready()`），被迫再繞一圈，多花 4.85 秒走**剛砍完的空地**（路線是閉合圈，第 2 圈以後都是走過的地）。

**重點**：`teleport()`（:492）內部本來就會自己等冷卻
```python
wait = _teleport_cooldown_wait()
if wait:
    rec({"note": f"等傳送石冷卻 {wait:.1f}s"})
    time.sleep(wait)
```
所以 filler 裡的 gate 只換來「站著等 0.55 秒」變成「走 4.85 秒空地」。**拿掉它不會動到 13 秒的安全保證**（點下去的時間仍是上一次傳送後 13 秒以上）。

- 影響：每輪冰島一趟 → 省約 4.3 秒；以 189 窗口/6 小時估，約 **13 分鐘**
- 風險：這會改到使用者當初「冷卻沒好就多繞一圈」的設計，**先問再改**

### B. `ISLAND_MIN_DWELL` 貼邊

`ISLAND_MIN_DWELL = 12.0`（:253），而 ice 第 2 圈邊界是 12.09s，只差 **0.09 秒**。手機一慢就會跳回 3 圈。
若要讓判定穩，建議放到 **11.5**（仍滿足「至少 12 秒」的實務需求，因為 teleport 內部會補足冷卻等待）。
一樣**先問使用者**，因為「至少 12 秒」是他定的。

### C. 空檔剩餘時間無法轉成收益

砍掉重複趟次後，窗口末端會出現 5～45 秒的「等樹」空檔（例如 §5 的 +221 → +226）。
這是結構性上限：4 趟 ≈ 64 秒、島上重生 108 秒，那段時間在現行機制下沒有地方換成木頭。

要真的吃掉它，唯一的路是**拉長主區路線**（使用者提過的「先掃整個農場 → 往內縮 → 再往外」同心覆蓋）。

- `captures/_reverted_20261029/corner_walk.jsonl`：量測紀錄

每次執行會寫 `captures/fixed_YYYYmmdd_HHMMSS/log.jsonl`。分析窗口結構：

```python
import json, collections
rows = [json.loads(l) for l in open("captures/fixed_XXX/log.jsonl", encoding="utf-8") if l.strip()]
ISL = {"ice", "shark", "duck", "truffle"}
def secs(t):
    h, m, s = map(int, t.split(":")); return h * 3600 + m * 60 + s
ev = [(secs(r["t"]), r["note"]) for r in rows
      if r["note"].startswith("傳送 ") or r["note"].startswith("=== 第")]
win, cur = [], []
for t, n in ev:
    if n.startswith("傳送 ") and n.split()[1] in ISL:
        cur.append(n.split()[1])
    else:
        if cur: win.append(cur); cur = []
for w in win:
    dup = [a for a, c in collections.Counter(w).items() if c > 1]
    print(len(w), "趟", " → ".join(w), "重複:", dup or "無")
```

每一趟的圈數／停留：抓 `r["island"]` 與 `r["dwell_s"]`，最後一筆 `r["decision"]` 就是決策（`switch` / `return`）。
