# Pickaxe King Auto

自動化《Pickaxe King Island》（Android `com.rogueuniongames.pickaxekingisland`）的素材採集。

**作法是純機械化固定流程**：不偵測畫面、不判斷該砍哪棵樹、不做任何驗證或重試。
固定座標傳送、固定 px 路線走路，走過去遊戲就會自動揮鎬。

## 現況（2026-10-26 改成排程器）

- **不再走「固定一輪三區」**，改成**只去已經刷新的地區**（`REFRESH`）：
  小村莊／起始之地 100 秒（樹重生）、自由農場A 240 秒（作物 4 分鐘）。
  以前固定一輪 98 秒、農場卻要 240 秒才刷新 → 每 2.4 趟就有 1.4 趟白跑。
- 三區都在刷新中就**等到最快好的那一個**（log 會印「等 小村莊 刷新 17s」），
  空下來的時間是留給其他場地的，不是拿去空跑。
- 實測一趟：小村莊 18s（含珍珠 6s → 25s）、起始之地 21s、自由農場A 40s（6 組補時）。
- 模擬 30 分鐘：小村莊 15 次、起始之地 15 次、農場 8 次、珍珠 3 次 → **62% 在做事、37% 空檔**。
  空檔就是還能塞幾個場的額度（`tools/schedule_sim.py`）。
- **傳送石冷卻 12 秒**（使用者確認）：冷卻中再點不會傳送，選單會留在畫面上，
  之後的手勢就打在那個選單上。程式已在 `teleport()` 加保護，間隔不足會先等。
- 珍珠附掛在小村莊（不單獨跑一趟），冷卻 600 秒，去回都用最快拖 720（794px/秒）。
  實測來回後偏移 4～12px，等於精準回到傳送落點。
- 小村莊第 2 個移動動作（北 1000 後的西 150）是刷新排程的第一刀基準；主區依序處理小村莊、起始之地，
  農場只有在 240 秒刷新後才回去，北 600／西 350 進場後，固定執行 4 組東 700 → 西 700 採收循環（FILL_PAIRS=4，總共四組，不是額外組數），不因村莊樹到期中斷；之後用剩餘時間補島到基準後 105 秒。
- 補島**固定順序、不抽選**：冰雪魔像 → 鯊魚 → 鴨子 → 松露，排除剛離開的那座。
  不看重生時間（那是大約值，見「遊戲事實」）。
  **同一個補空檔窗口內每座島只去一次**（逛完四座就回主區等樹）：外圈放大後一趟約 18 秒，
  四趟約 72 秒，而島上重生要 100 秒以上，所以第五趟起等於走同一塊空地、收益接近 0。
  前兩段進場只走一次，後四段是一個**生怪區滿版的外圈**（實測 1000×844；2026-10-30 實走定案：東/西 1000、南/北 850）。
- 之後是**四段螺旋向內掃描**：方向照 南→東→北→西 循環，每兩段各縮 `ISLAND_SHRINK_PX = 100px`
  （`px = base - 100 × (i // 2)`）。以冰雪島（西北角進）為例：
  ```
  第 1 圈：南 850、東 1000、北 750、西 900
  第 2 圈：南 650、東 800、北 550、西 700
  第 3 圈：南 450、東 600、北 350、西 500
  ```
  為什麼不是「閉合圈每圈縮 10%」——閉合的 4 段矩形一定回到自己出發的角落，
  只縮短四段會貼著原本兩條邊重走（第 2 圈約 1674px 白走）。螺旋不閉合，
  缺口由「上一段少走 100」自然產生，每段都是沒走過的地，也不用多送「往內挪」的手勢。
  前兩段一定會撞牆（南是柵欄、東是水），牆會把位置夾回來，所以螺旋被牆釘住不會累積偏移。
- 每次進島後以 `perf_counter` 計實際停留，至少 12 秒（從傳送載入等待結束起算）；到循環邊界滿 12 秒時：期限已到就結束補島（傳送石冷卻由 `teleport()` 自己等），尚未到期就換下一座沒去過的島。滿版外圈**兩圈**就達到最低停留，可提前換島；未滿 12 秒則繼續當前島的下一圈，不開愛心／選單、不原地睡眠。四座都逛過就結束補島回主區，不會原地重複繞。
- 不設剩餘 25 秒或其他進島門檻：即使只剩幾秒，只要還有沒去過的島就換島（新的島是空手可採的），新島仍須待滿 12 秒並走完整圈。補島本身不傳回村，由主流程 `run_area()` 負責唯一一次村莊傳送；傳送冷卻從目的地點擊完成起算，不從點愛心起算。
- `--minutes` 到期不開始下一站；若正在補島，先完成當前圈、最低停留與冷卻，再停止，不額外傳回村。主區仍完成已開始的完整流程。

## 排程怎麼運作

```
REFRESH = {"village": 100, "start": 100, "farm": 240,
           "ice": 0, "shark": 0, "duck": 0, "truffle": 0}   # 秒；島嶼 0＝不設門檻
```

每一步由 `next_stop(now, last, village_first_cut)` 決定去哪；小村莊的第一刀時間是新一輪的權威基準：

1. 只挑**已經刷新**的地區（`now >= 上次開始採集 + REFRESH`）。
2. 多個都好 → 挑**超過自己週期比例最大**的那個（用比例而非絕對秒數，
   否則一趟走得比刷新還久的地區會永遠最超時、把其他區餓死）。
3. 第一刀基準未滿 105 秒時，小村莊不會提前回去；主區都不能去時，主迴圈會用島嶼填空，沒有可安全進入的島就實際睡眠，不 busy-loop。

**補空檔的調配怎麼算**（2026-10-29 由 6 小時執行紀錄統計）：

| 單位 | 實測耗時 |
| --- | --- |
| 一趟島（傳送 → 下一座傳送） | 舊外圈（800×400 級）13.6～15.2s；滿版外圈約 18s（待實機驗證） |
| 島上一圈（滿版 1000×850） | 約 7.3s（3700px ÷ 552px/秒 + 手勢開銷） |
| 小村莊一站 | 18.5s |
| 起始之地一站 | 20.2s |
| 自由農場A 一站 | 40.4s |

所以一個 105 秒窗口扣掉主區跑掉的時間，**剩下多少就塞幾趟島**，但上限是四趟：
四趟約 72 秒，第五趟回到第一座時它才過 72 秒、還沒重生（約 108 秒），等於白走。
逛完四座就回主區等樹，不會為了把時間填滿而重複繞同一座島。
若某個窗口很短（例如農場剛好插進來，只剩 30 秒），就只跑一趟。

**加新場地**：`ROUTES` 加路線、`LABEL` 加名稱、`REFRESH` 加刷新秒數，排程器自動排進去。
`tests/test_schedule.py` 會擋下「加了路線卻忘了登記刷新時間」的情況。

`--cycles N` 只計小村莊／起始之地／自由農場A（`--cycles 1` ＝三個主區各一次）；島嶼補空檔不增加站數。

## 執行

**雙擊 `Pickaxe-King-Auto.bat`：完全不用輸入，它會自動偵測手機，按一個 Enter 就啟動，開始無限循環**（遊戲開著即可），不再預設四小時結束。
偵測由 `pkauto/adb.py` 的 `detect_target()` 負責（啟動器呼叫 `python -m pkauto.adb`），優先序：**無線偵錯的 mDNS 名稱 → 無線 IP:PORT → USB**。mDNS 名稱（`adb-<序號>-<後綴>._adb-tls-connect._tcp`）**跨埠跳動穩定**，所以不需要手輸埠號，也不需要固定埠 5555。實測：3 分鐘內換了 11 個埠，名稱全程不變；埠穩定後用名稱連續 16 次指令全成功。
找不到任何裝置時會停下來並提示要開無線偵錯或接 USB，不會靜默繼續。
adb 沿用 scrcpy 內附的 `D:/Tools/scrcpy-win64-v3.3.4/adb.exe`（36.0.0），可用 `PKAUTO_ADB` 覆寫。啟動器會先檢查本機 ADB server；若沒有回應，在啟動階段執行一次 `kill-server`／`start-server` 後重新檢查。
採集途中 adb 這一層若斷掉，由 `pkauto/adb.py` 自動恢復並重送那一個指令（見下方說明），不會整個流程中斷。啟動器把偵測到的 target 設為 `ANDROID_SERIAL`；有設定時每個指令都以 `adb -s TARGET` 固定 transport。
停止：先點選執行視窗，再按 Ctrl+C，程式會中止當前流程並關閉 log，不必等整輪跑完。
console 只印開始、輪次、傳送到哪、開始採集（結束時印收工）；逐段細節仍寫在 `captures/*/log.jsonl`，要看即時逐段加 `--verbose`。
若 CMD 詢問是否終止批次工作，輸入 Y 再按 Enter。

```bash
P=./.venv/Scripts/python.exe
$P cycle_fixed.py --minutes 240     # 跑 4 小時
$P cycle_fixed.py --dry-run         # 只印逐段編號與按住毫秒，不動手機
```

調某幾段 px 時不用跑整輪：

```bash
$P run_leg.py village 1 2 --no-measure            # 傳送後只走第 1、2 段
$P run_leg.py village --walk L:100 --no-measure   # 從現位置往西 100px
```

調參工具的 `--settle` 是移動放開後的停頓秒數，`--settle-first` 可單獨指定第一段；
不再疊加主循環的 2.15 秒。需要量測時，畫面顯示與 tune log 共用同一次量測；
長腿拆段會加總位移、取最低分數並合併來源，不另算首尾影像。

**adb 這一層斷掉**時，`pkauto/adb.py` 會重試同一個指令，最多 3 次，每次間隔 1.5 秒。
**恢復方式依錯誤層級分流**：daemon 層級錯誤或逾時 → `kill-server`／`start-server`（無線 IP:PORT 再 `connect`）；
裝置暫態（`device offline`／`not found`／`still connecting`／`still authorizing`）→ **只等待重送**，IP:PORT 才補 `connect`，mDNS 名稱交給 adb 自動重連，**不砍 server**（砍掉會摧毀所有 transport，對暫態太重）。
console 會印「ADB 無回應（原因），重啟 adb server 後重試」或「…等待裝置就緒後重試」。

判斷原則是「**指令到底有沒有送到手機**」，不是錯誤字面：

- **沒送到 → 重送安全**：`daemon still not running`／無法連 127.0.0.1:5037、
  `device 'IP:PORT' not found`（實機 `kill-server` 後就是這個）、
  `device offline`（含 `(no transport)`／`(transport offline)`）、`device still connecting`、`device still authorizing`。
  這些全部在 AOSP 的「選 transport」階段就被拒絕，`shell:input swipe` 字串根本沒寫出去（原始碼依據見「已知」）。
- **可能已送到 → 重送會多走**：指令卡到 timeout（滑動與其餘皆 30 秒，遠長於任何一個手勢）。
  目前仍重試最多 3 次，所以那一段最多可能多走 3 次；偏移只影響當前這一站，下一站傳送就歸零。
  實機測試：連續 3 次逾時會停下來並印最後一次的原因，約 30 秒，恢復後 adb 仍可正常使用。
- **確定已送達、但指令本身失敗**（例如手機回 `sh: xxx: not found`、`error: closed`）→ 不重試，直接停下來顯示原因。

重試滿 3 次仍不行才停下來，錯誤訊息會註明「已重試 3 次、重啟 server N 次仍失敗」。
這不包含遊戲內的傳送成功判斷，仍維持純機械化、不偵測畫面。

## 換算（調參只改 px）

- 移動是搖桿式：**第一次按下的點是搖桿原點，拖越遠走越快；按住時間＝走的時間**。
- **速度表 2026-10-26 重標**（遊戲內跑速變快，舊表整組失效）。現值（px/秒）：
  拖 85→155、250→466、300→552、500→721、1200→866、1800→903、2000～2400→919。
  按住毫秒 = `px ÷ 速度 × 1000`，下限 110ms。
  量法：`test_drag.py --hold 1200`（固定按住、只改拖曳長度）＋ `run_leg.py` 交叉驗證。
- **平台在拖 2000 以後**：2000→917、2100→910、2200→920、2400→915（各 2 筆），
  全在 910～924，差異在誤差內 → 天花板 ≈919px/秒。拖 1800 已是天花板的 98%，
  所以林外（進場段）用 `ENTRY_DRAG=1800`，不必讓手勢橫跨整個螢幕。
  舊表在拖 500 就夾住（541），實測卻一路到 919 → 搖桿沒有在 500 飽和。
- 進場 850px 的按住：1571ms（舊表）→ 981ms（拖 1200）→ **941ms（拖 1800）**。
  實測 850px 走 856px（誤差 0.7%）。林內用 `FOREST_DRAG=200`（372px/秒）。
- **全域速度先不動**：遊戲的跑速與砍速都還會再升、有些路線之後可能整段不必走，
  現在把速度調死會白做 → 漏砍用「停頓」與「單段覆寫」解決，等路線定稿再重標一次。
- **修漏砍的首選是停頓 `SETTLE`，不是降速**：實測每段停 2 秒「樹就都砍掉了」。
  機制是漏的樹在**段終點附近**（走到定點時還差一兩刀，下一段一拉走就永遠不會再砍），
  停下來就留在同一棵樹的攻擊範圍內。停頓不影響移動速度、不位移終點。
- **px 和拖曳是兩個獨立旋鈕**：漏砍時**加停頓**（其次才是調拖曳），**不要加 px**
  （終點會位移，開環路線收不回來）。加了停頓仍漏的那一段就寫單段覆寫 `("N", 125.0, 140)`。
- `SPEED_SCALE` 是給「日後又調速度」用的備援旋鈕，目前 1.0；曲線形狀已被改過，
  所以它不等於整張表等比，只在確定形狀沒變時可用。量法見 `run_leg.py` 開頭。
- **路線 px 不要跟著速度改**：那是地圖幾何，速度變了要改的是按住毫秒。
- **東西向拖曳上限 720px**（`DRAG` 起點 (720,2600)，拖曳終點必須留在 1440 寬的螢幕內）：
  橫向最快 794px/秒（表上 700→791），比縱向的 903 慢約 12%。往南上限 520px（y 到 3120）。
  想再快只能把起點往反方向移（往西改從 x=1140 起手），但那已貼右側 UI 欄，未驗證。
  滑動一律從畫面中央起手，終點落在邊緣不會觸發 Android 的返回手勢。
- 單段按住上限 3000ms，超過就平均拆段。
- **刻意不做靜態補正**：跨場次的實際速度差 ±3.5%（同一條 800px 腿曾量到 771 / 835），
  比平均偏差 1.5% 還大，補了反而在快場次多走。詳見 `cycle_fixed.py` 的註解。

## 設計原則（踩過的坑換來的）

- **走過去就會自動砍**，所以不需要找樹，只需要穩定的走路路線。
- 傳送石位置會浮動、有冷卻，但實測 (1340,1670) 命中 1.00 → 固定點擊即可。
- 選單是固定面板：格子座標固定、直接點；長滑只是保險（screenrecord 逐格分析過，位移 0）。
- 休息對話框固定在 (721,1839) → 直接點，不需偵測。

## 已知（adb 斷線調查，2026-11-22）

2026-11-21 22:31 那次跑到 111 站、1 小時 34 分後崩潰，錯誤是
`cannot connect to daemon at tcp:5037 ... (10060)`。查證結果（診斷指令碼在 `captures/`，不進版控）：

- **10060 = Windows WSAETIMEDOUT；21 秒是 TCP connect 的 SYN 重試預算（3+6+12）**。
  實測對黑洞 IP 下 `adb connect` 花 21.05 秒回報 10060，與 log 的 21 秒空檔吻合。
- **server 沒有死**：`adb.log`（路徑由 `adb server-status` 指出，跨 session 追加）顯示
  當時的 server PID 6948 從 11-14 一直活到 11-22 16:19，崩潰後 03:48 仍在寫日誌。
- **transport 也沒斷**：那條無線 TLS transport 22:31:10 建立、03:48:58 才 read failed。
- 所以是「**server 活著但暫時不 accept 連線**」，**確切觸發點仍未鎖定**。已排除：
  對外 blocking connect 卡住事件迴圈（黑洞 connect 那 21 秒內 101 次 USB 探測全成功、最慢 0.08s、PID 不變）；
  adb 的 socket flush 逾時（原始碼 `deferred_close` 只有 `fdevent_set_timeout(fde, 1s)` 且事件驅動）；
  電腦睡眠（System log 無 Kernel-Power，`STANDBYIDLE` AC/DC 皆 0）；崩潰當下無任何系統事件。
- **port 跳動不是這次的原因**（崩潰時埠正常），但它是另一個獨立故障源：
  日誌裡出現過 34587／39227／44643 三個不同埠。**已用自動偵測解決**（2026-11-22 實測）：
  mDNS 服務名稱 `adb-<序號>-<後綴>._adb-tls-connect._tcp` 的後綴，在 3 分鐘內 11 次換埠中**全程不變**；
  埠穩定後用該名稱連續 16 次指令全成功。churn 期間的失敗是 `device '…' not found`（52 次）與
  `device offline`（47 次），兩者都是「指令沒送到手機」的暫態，重試即可。
  因此啟動器改用 `detect_target()` 自動偵測，**不再需要固定埠 5555，也不需要手輸埠號**。
- **本機無線 TLS 的長期病歷**：`adb.log` 累計 108 次 `SSL_read failed [invalid library (0)]`、
  10 次 `SSLV3_ALERT_CERTIFICATE_UNKNOWN`、3 次 `SSL_write failed`；
  openscreen mDNS 在 11-08 有 9 次 `WSASendMsg() failed (10065)`／`mdns_sender.cc:46 Error sending packet`。
  upstream 多次修過 mDNS 帶垮 server（33.0.1 Windows mdns crashes、35.0.2 截斷查詢、37.0.3），
  且 **37.0.1 直接刪除 openscreen**（實測 37.0.1 二進位裡 openscreen 字串數 0，36.0.0 是 37）。
  **但這些只是「有病歷的故障面」，不是已證實的崩潰原因**：崩潰當下日誌沒有 mDNS 錯誤、
  TLS transport 也還活著。曾據此升級 37.0.1＋`ADB_MDNS=0`，**因根因未確認已退回**
  （使用者決定：先測試確定根因再實作）。37.0.1 仍裝在 `D:/Tools/platform-tools/`，目前未使用。
- **`device offline` 可以安全重試**（原本以為不行，已修正）。AOSP `android-16.0.0_r1`：
  `transport.cpp` 的 `acquire_one_transport()` 在 `case kCsOffline` 就把 `result = nullptr`；
  `client/adb_client.cpp` 的 `_adb_connect()` 先 `switch_socket_transport()`、失敗即 `return -1`，
  之後才 `SendProtocolString(fd, service)` → 指令字串沒寫出去。
  `sockets.cpp` 的 `smart_socket_enqueue()` 兩個 `device offline (...)` 變體也都在 `connect_to_remote()` 之前。
  中途斷線時用戶端看到的是 EOF／RST／`closed`，不是 `device offline`。37.x 這幾處原始碼未變。
- **21 秒 stall 的根因仍未確認，調查繼續中**。自動偵測只解決了「埠跳動」這個已確認的獨立故障源，
  **不宣稱能解決 stall**。診斷儀表已建好並通過 30 秒 smoke：`captures/stall_watch.py`（每秒測 5037
  accept 延遲＋server CPU 時間，可區分「被阻塞」與「忙等」）、`captures/proxy_load.py`（零重試代理負載，
  不觸碰螢幕）、`captures/overnight_stall_test.py`（編排 traced server，`ADB_TRACE=fdevent,mdns,sockets`）。
  **長時間重現尚未跑**；原本那次是 1h34m 才掛。重試機制保留作為保底（使用者已同意）。
- 其他觀察（**候選嫌疑，沒有證據**連到那次 21 秒）：這台是 Modern Standby（S0，S3 不可用）；
  裝有 SoftEther VPN（`SeLow_x64.sys` 綁 Wi-Fi、`Neo6_x64_VPN.sys` 執行中，VPN 網路卡 Disconnected）
  與 Defender `WdNisDrv`，都是網路堆疊裡的過濾驅動程式。
- 手機是 **Android 17**（`ro.build.version.release`），不是舊文件寫的 16。
- `adb tcpip 5555` 只寫 `service.adb.tcp.port`，**不持久**：重新開機即失效，需接 USB 重下。
  5555 是**明文 adb**，區域網路內任何裝置都能連（無線偵錯至少有 TLS）——這是安全性取捨。

  位置在林內（北 850 → 東 300 附近），但為了插拔要加小段回頭、誤差會累積，
  使用者判斷效益不高。冷卻中點擊實測「什麼都不會動」，所以日後若要做，
